# Agent Notes

这里存放一种设计文档。**Agent Note** 记录影响本仓库的决策或提案：为什么这样定、放弃了什么，也就是代码和文档承载不了的部分。本文件规定 Agent Note 放在哪里、什么时候写，以及 [文件格式](#文件格式)。

## 目录与命名

每个 Agent Note 有两个维度，都编码在**路径**里：`{生命周期}/{类别}/yyyy-mm-dd-主题.md`。主题用小写英文单词加连字符（kebab-case），例如 `2026-10-24-npm-distribution.md`；文件名会出现在链接、命令行和 git 输出中，非 ASCII 文件名在部分终端和工具中会出现编码问题。标题和正文仍用中文。

- **生命周期**（顶层目录）是 Note 的状态，状态变化时 Note 在目录之间移动：
  - **`proposed/`**：实现前评审的提案；尚未实现（或只实现了一部分）。
  - **`implemented/`**：决策已落地。文件记录决定了什么、否决了什么，并且**与实际落地的内容保持一致**：之后代码移动了文件、改了包名、换了配置键或默认值时，在同一次改动中更新 Note（只更新路径、名称、结构等事实，不改决策本身）。见 [implemented/AGENTS.md](implemented/AGENTS.md)。
  - **`rejected/`**：提案经过考虑后被否决。只在它的理由能防止一个诱人且有影响的错误时保留；否则删除。
- **类别**（下一级目录）是决策的*种类*，见下文 [分类](#分类)。

文件名中的日期是这个主题**首次提出**的日期（以 git 历史为准）。Agent Note 之间的引用使用相对路径的 Markdown 链接，不用纯文字或编号，这样在 Note 跨目录移动后仍能检查和维护。

生命周期目录本身就是清单：浏览各生命周期和类别目录，或在仓库中搜索。不要加集中的 `INDEX.md`：它重复了路径中的信息，还会让无关的 Note 改动在同一个文件上冲突。

## 分类

每个 Agent Note 属于下列封闭集合中的一个类别，类别编码在路径中。新增类别需要更新本节。

| 类别 | 覆盖范围 |
|---|---|
| `feature` | 新的、面向用户或模型的能力。 |
| `bug-fix` | 修正一个缺陷，或补上一个已发现的缺口。 |
| `simplification` | 删除代码、行为或对外接口，不增加能力。 |
| `architecture` | 关于**发布的源码**的结构性决策：包之间的关系、运行时的概念。 |
| `process` | 代码**周边**的工具、策略或工作流：检查、包管理器、发布流程，而不是运行时行为。 |
| `testing` | 测试基础设施和策略。 |

`architecture` 和 `process` 的分界：**architecture** 关于我们发布的源码；**process** 关于周边的工具和工作流。（刻意不设 `refactor`：它与 `simplification` 重叠，后者的判别标准 "可观察的行为是否改变？" 已经覆盖了它。）

## 合并与删除

只描述小的 UI 调整或纯机械性改动的已落地 Note 直接删除，并修复或移除指向它的链接。局部的缺陷修复、性能改动、新能力或实质性的行为决策，不会因为实现规模小就符合删除条件。被否决的 Note 只在能防止一个合理的错误时保留，否则删除。

被完全取代的已落地 Note 可以合并进当前拥有该决策的 Note 后删除。删除前，拥有者必须保留每一条独有的理由、备选方案、后果、必需的验证和指明的覆盖缺口，并修复所有指向它的链接。部分取代不符合条件：两个 Note 都保留并互相链接，更新每一条仍然成立的事实。合并不能把旧文件改写成相反的意思，也不能让 git 历史成为理由的唯一副本。

## 什么时候写

只在代码、测试和现有文档都解释不了的**长期决策理由**出现时，在同一次改动中新增或更新 Agent Note。对未来较大工作的提案从 `proposed/` 开始；已经做出的决定从 `implemented/` 开始。按决策选择对应的类别目录（见 [分类](#分类)）。

更新已经拥有这个决策的 Note 即可满足要求，不要再建一个重复的。机械性或局部的改动不写，包括局部的 UI 展示和交互调整。Agent Note 永远不会被改写成*另一个决策*：用一个新 Note 取代它，并让两个 Note 互相链接。在 `implemented/` Note 中更新其现有决策的落地位置是必须做的，不是禁止的，见 [implemented/AGENTS.md](implemented/AGENTS.md)。

## 文件格式

### 头部

每个 Agent Note 的前三行固定为：

```markdown
# Agent Note: <标题>

Status: <状态>
```

后面空一行。`# Agent Note:`、`Status:` 和三种状态值是固定的英文标记，`<标题>` 和否决原因用中文；正文章节名用下文规定的中文名称。`Status:` 的值有三种形式，并且必须与文件所在的生命周期目录一致：

- `Status: proposed`
- `Status: implemented`
- `Status: rejected — <一行说明原因>`

状态行不写日期，也不加括号说明：文件名保存首次提出的日期，其余都在 git 里。"以修改后的形式通过" 属于正文内容（在陈述决策的地方写出修改）。否决原因是唯一带内容的状态，因为读者打开一个被否决的 Note，要找的正是这个结论。

### 正文骨架

每个 Agent Note 的正文都以 `## 问题` 开头：动机，写成不依赖解决方案也能独立成立的样子。后面的内容取决于生命周期；反复出现的章节只使用下面的标准名称，真正特有的技术章节（包的拓扑、传输协议、schema）可以自由放在必需章节之间。

#### `proposed/`

```markdown
## 问题
## 提案
…特有章节…
## 考虑过的替代方案
## 验收标准
## 风险
```

`## 提案` 是打算做的改动，可以用将来时：工作还没实现时，计划、迁移步骤和未决问题都放在这里。`## 验收标准` 说明什么样的可观察状态算完成。`## 风险` 既包括可能出错的地方，也包括这个改动明知要放弃的东西。

#### `implemented/`

```markdown
## 问题
## 决策
…特有章节…
## 考虑过的替代方案
## 后果
```

`## 决策` 用现在时描述已落地的现实，整个文件按 [implemented/AGENTS.md](implemented/AGENTS.md) 与之保持一致。`## 后果` 记录这个取舍付出了什么**以及**换来了什么。提案阶段的章节标题在这里属于规格用语，不得出现：`## 提案`、`## 计划`、`## 迁移计划` 和 `## 验收标准`（[slop 清单](../../docs/AGENTS.md#slop-清单) 说明了原因）。用现在时陈述事实的 `## 测试`、`## 延期工作` 或 `## 相关` 章节可以有。

#### `rejected/`

被否决的 Agent Note 就是冻结的提案：保留它在提案时的章节（包括 `## 验收标准` 或 `## 计划`），结论写在 `Status:` 行上。只有头部、开头的 `## 问题`、一个 `## 提案` 章节，以及下面关于备选方案的强制要求适用于它。

### 考虑过的替代方案：必须写

每个 Agent Note 都有 `## 考虑过的替代方案` 章节：列出每一个真实存在过的备选方案和它落选的原因，每个方案一个以加粗开头的段落，或者对有争议的方案各写一个 `### 为什么不用 <X>？` 小节。一个只记录了决定、没记录它胜过了什么的决策，会招来反复争论，而这正是 Agent Note 要防止的。

备选方案只记录真实存在过的，绝不编造。确实没有可比较的方案时（例如决策直接由外部规范、上游约束或前序决策确定），写一段 `没有考虑过其他方案：<原因>`，并链接决定它的规范或 Note；只写 "无" 不算说明。

### 在生命周期之间移动

把文件移到另一个生命周期目录时，在同一次改动中更新 `Status:` 行，并满足那个目录的骨架。具体来说，`proposed/` → `implemented/` 要把 `## 提案` 改写成现在时的 `## 决策`，把 `## 验收标准` 和 `## 风险` 并入 `## 后果`（或者并入一个现在时的 `## 测试` 章节，说明现在由什么保证这个行为），并删掉计划，改写成实际落地的内容。`proposed/` → `rejected/` 只需要在 `Status:` 行加上原因，然后冻结文件。
