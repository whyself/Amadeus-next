# 面向模型的体验设计

- **先给最小上下文：** 先给出用途、可用操作和约束；详细说明在需要时再加载。
- **让发现路径明确：** 每个延迟加载的资源都需要清楚的描述和可靠的获取方式。
- **关键约束要可见：** 权限、破坏性效果和必需的校验，应出现在相关操作之前。
- **优先有界的输出：** 返回精简的结果，以及可用来获取详情的标识或路径；不要整份倾倒日志或文档。
- **利用局部性：** 在操作结果中附带有限的、很可能用得上的相邻上下文。例如返回一条讨论串回复时，带上它前面的几条消息。明确标出省略和截断，并提供获取更多内容的方法。
- **评估总工作量：** 节省上下文只有在不引起更多搜索、重复读取或错误时才有价值。

## 工具定义

- **删掉显而易见的约束。** 省略模型能从调用结果中学到的规则，例如读取不存在的文件会失败、发送失败的消息没有送达。
- **描述行为，而不是实现。** 写清工具做什么、返回什么；省略内部机制、模型会在结果里看到的输出标记，以及强制执行的细节。
- **参数规则写在参数上。** 默认值、取值范围、成对出现的要求和何时设置的规则，属于该参数的描述或 schema；如果工具描述会随配置变化，变化的那部分通常应该做成参数。
- **每个事实只说一次。** 不要在系统提示的段落里重复工具定义，不要在工具描述里重复参数描述，也不要在一个工具里重复另一个工具的规则。
- **度量改动。** 修改工具定义前后，比较第一轮对话的 prompt token 数。
