# Amadeus-next 文字规范

先写够保留契约所需的内容，再删掉推理过程、重复和装饰。契约指调用方、被调用方、实现方、生产者或消费者所依赖的义务、不变量、前置条件、后置条件或兼容性承诺。本 skill 负责编辑上的取舍和文字的必要覆盖；文档的分层与放置见 [docs/AGENTS.md](../../../docs/AGENTS.md)，排查推理过程泄漏用 [amadeus-trim-cot-leakage](../amadeus-trim-cot-leakage/SKILL.md)。它是指导，不是脚本。

把 "契约"、"边界"、"形态"、"表面"、"接缝"、"门禁"、"词汇" 这类词当作使用前要检查的词，而不是禁用词。先问一句：确切的规则、API、字段集合、类型、校验、时机、组件拆分或失败方式，能不能更准确地表达这件事？当这个词正好命名了确切的技术对象（包括调用方与被调用方之间的契约、安全或进程边界）时保留它。

注释描述代码无法表达的非显然契约或理由；不复述代码已经表达的内容。

## 输入与排除

要求明确的 `scope`。缺少时报告需要的输入并停止；不要自行推断为全仓库，也不要开始追问。

接受 `mode: automatic | interactive`，默认 `automatic`。只有用户明确要求提问或校准时才进入 interactive 模式。

`mode` 决定是否提问，不决定写权限。审查和审计任务只报告发现、不修改；用户明确要求写、修或精简时才应用明确的修改。

始终排除 `node_modules/`、`lib/` 等依赖和构建产物，即使请求的范围是整个仓库。

## 保留完整命题

修改前先找出段落中的每一个命题，并保留每一个相关的：

- 行为主体与动作；
- 条件、时机与顺序；
- 情态，例如必须、可以、绝不；
- 否定性保证与例外；
- 所有权、副作用、失败方式与后果。

只有当每个事实性子句都保留下来、结果也更清楚时，才删掉形容词、重复和叙述。字数变少本身不算改进。

在使用处保留完整的局部契约：调用方或维护者在那里需要的行为、失败、所有权和后果。架构、理由、算法、历史和扩展示例积极链接到拥有它的文档。一种解释只有一个归属；必要的契约事实可以在局部重复。

非显然的理由，如果省略后可能导致误用或错误的简化，就保留；否则写出后果并链接到理由的归属。

## 按位置要求的覆盖

这不是单向的删减。当代码、类型和结构无法传达下面要求的契约时，补写或恢复文字；当这些事实在局部已经显而易见时，不要加注释。

- **公共 JSDoc**：写出调用方可见的返回值区别、抛出或拒绝、副作用、所有权、时机、取消和持久性。
- **内部注释**：说明非局部的结构和明显复杂的局部结构，包括不变量、竞态顺序、所有权、安全边界和出人意料的失败行为。删掉控制流叙述和对代码的复述。
- **模块注释**：写出模块的角色、依赖、职责和非显然的架构选择；架构选择链接到拥有它的说明。
- **测试**：只解释非显然的测试设计，即为什么需要某个 fixture、断言、平台适配、真实入口或间接观察。删掉逐步讲解和清单。
- **操作指南**：包含前置条件、必须执行的操作、真实入口、可观察的验证和简洁的警告。
- **包 README**：包含使用方的契约：安装、配置、语义、失败、限制、扩展点和对模型可见的影响。引用本包拥有的稳定的模型可见文字；跨包的内容链接到其归属。保留长期存在的缺口和维护陷阱，不写普通的清理清单。
- **Skills 和 agent 指令**：写出行为护栏和明确的范围限制，例如 "这是指导，不是脚本"。工作流保持简洁，并链接到事实来源。
- **示例和配置注释**：解释访问限制、非显然的接线或加载顺序、安全立场、例外和容易出现的误用。不要叙述配置本身已经展示的条目。
- **Prompt 和可见文字**：措辞就是行为。界面文案放在 locale 字典里；文本、无障碍名称、提示、占位符和格式模板一起检查。修改模型或用户可见的文字时，要有对应的行为验证；授权范围内没有可验证的场景时，保持原文不变并报告推迟。
- **诊断信息**：写出失败的对象或路径、违反的规则，以及不显然时的修正方法。删掉内部执行过程的叙述。

保留可搜索的机制名称，以及有意义的情态、时间或否定强调。只统一装饰性的强调。

## 工作流程

1. 确认范围、模式、当前分支，以及适用的 `AGENTS.md` 文件。不要查看无关的分支。
2. 判断一段文字之前，先读 [docs/AGENTS.md](../../../docs/AGENTS.md) 和拥有它的代码或文档。需要校准或遇到不熟悉的情况时，读 [提炼的例子](references/examples.md)。
3. 检查请求范围内的全部内容，不只是最大的文件。用搜索和字数统计找出候选，再从语义上判断。
4. 把每个候选归为保留、补写、精简、恢复、重组或推迟。只有任务授权修改时才应用明确的修改；不要为了达到删减目标而制造修改。
5. 学到新规则后，回头检查类似的段落。
6. 运行相关的窄范围检查和 `git diff --check`；可见文字的改动要运行对应的行为验证。
7. 报告检查过的范围、明确的修改、有意保留的内容、推迟的情况，以及实际运行过的检查。

## 两可的情况

只有当至少两种写法都满足完整命题规则、但在已接受的原则之间有取舍，且本 skill 没有给出答案时，才算两可。只有一种保留命题的改法时，不算两可。

在 automatic 模式下，获得授权时应用明确的修改，把真正两可的情况报告出来，不提问。不要为了推进而削弱命题。

在 interactive 模式下，把相似的段落按适用的原则归组。给出两到三种可行的写法，推荐其中一种，并说明它们在事实或结构上的区别。不要提供明显更差的干扰选项。

用户做出决定后，把原则和各种写法提炼进 [例子](references/examples.md)，不写讨论经过，并把学到的规则应用到范围内所有类似的段落。
