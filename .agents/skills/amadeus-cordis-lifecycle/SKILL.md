# Cordis 所有权与生命周期审计

这是针对 Cordis 所有权和生命周期的专项语义评审。仓库审计从导出的插件入口开始（`apply`，或由 Cordis 调用的具体默认导出），再追踪从这些根可达的模块初始化、注册的服务、监听器、effect、销毁函数和传递调用。无关的辅助函数、构建工具、CLI 路径和测试不作为问题目标。可以阅读测试和 Cordis 源码来确定行为；生成代码中的缺陷报告到拥有它的源码上。不在本 skill 下报告 Cordis 自身的缺陷。

## 事实来源

- [仓库约定](../../../AGENTS.md)：Cordis 所有权要求。
- [生命周期与 effect](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.1-rc.3/docs/cordis-tutorial/02-lifecycle-and-effects.md)：effect 的获取与释放。
- [服务](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.1-rc.3/docs/cordis-tutorial/03-services.md)：依赖跟踪与服务可用性。
- [防御规则](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.1-rc.3/docs/defensive-patterns/general.md)：等到静止后再拆除，以及必需的完成监听器。

## 评审流程

1. 找出从所要求的插件根可达的可变状态的所有者、注册、资源获取和工作准入。范围较大时，分目录独立扫描，再合并涉及同一消费方和同一资源的问题。
2. 沿实际的上下文追踪所有权：在可追踪的服务方法中，`this.ctx` 是调用方的上下文。确定每个 effect 归谁所有，以及释放它的是哪个销毁函数。
3. 沿每一个 await 追踪清理过程，一直追到最后一次服务调用、发出的事件、得到确认的操作和持久化写入。包括间接的事件投递，以及在 abort、kill 或取消之后执行的清理。
4. 把消费方的完成时间，与每个必需的监听器、注册表、写入器、连接、域或传输变得不可用的时间进行比较。查看当前 Cordis 的实现；仅凭启动顺序相反和依赖注册，不能确定完成顺序。
5. 构造一个合法的、会失败的交错执行顺序，以及可观察的影响。报告之前，先检查已有的取消、显式的先后顺序和有文档说明的丢弃语义。可行时用受控的 promise 复现；只从源码推断出的问题要如实标注。

## P0：单例模式

标记这样的情况：一个进程级的实例或可变状态的所有者，它的身份或生命周期来自模块加载、静态字段、全局 symbol、隐藏的缓存或 `getInstance()` 访问器。弱引用键、大小上限、代际检查和不改变行为的记忆化，都不能让模块级缓存获得 Cordis 所有权。

不可变的标量常量、纯粹的冻结表、无状态函数，以及在显式作用域的所有者内部分配的对象，不在此列。建议改为 Cordis 服务，加上声明的或以其他方式解析的消费方依赖；生命周期更窄时，使用作用域上下文或由服务拥有、按键索引的记录。

## P0：未撤销的副作用

标记这样的所有者：销毁之后还留下仍在生效的东西，包括监听器、注册、定时器、文件监视器、子 fiber、进程、连接、临时文件、订阅、对环境的修补或异步工作。如果清理可能在所拥有的工作停止之前就返回，那么只发出 abort 或 kill 而不等待其结束，就算违规。

正确归属的 `ctx.on()`、`ctx.plugin()` 和 `ctx.effect()` 注册本身已经提供了撤销，调用方不需要保留它们返回的销毁函数。不受管理的资源需要一个被拥有的 effect，或显式的、被 await 的清理。不要要求回滚有意为之的持久化写入或远程修改；但这些操作用到的临时资源和仍在生效的资源，仍然需要所有者。

## P0：清理依赖在消费方完成之前被释放

完成清理所需的任何服务调用或事件投递，都是生命周期依赖。在消费方结束之前（包括最终结果的发布和持久化写入），它实际使用的资源和监听器都必须保持可用。提供方的销毁 promise 在消费方之后才完成，并不能证明它的资源在消费方清理期间一直存在。

当前的 [fiber 卸载](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.1-rc.3/vendor/cordis/src/fiber.ts) 会并发启动同级的销毁函数。[服务撤回](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.1-rc.3/vendor/cordis/src/reflect.ts) 在自己的销毁函数内等待依赖它的 fiber，而同级的资源关闭函数此时可能已经在运行。加上 `inject`、反转注册顺序或保留服务引用，都修不好这个竞态。监听器也可能属于消费方的 fiber，并随着某个操作的排空一起自动取消订阅。

要求显式的所有权和被 await 的先后顺序：先停止准入，在依赖仍然可用时让已准入的消费方结束，然后再排空并释放资源。拒绝新的准入和完成已接受的操作，要分开处理。使用显式组合的 effect，或者使用一个拥有资源的父级，下面挂一个被 await 的消费方或服务子级；要核实实际捕获的销毁函数身份。`ctx.effect(function* ...)` 会串行执行它收集到的销毁函数，但包在一个独立注册的 effect 外面的包装器，并不会转移原 effect 的所有权。插件顶层的 generator yield 并不普遍保证同级销毁会串行执行。失败路径也要检查：一个清理错误不能导致跳过必需的 abort、结束等待或资源释放。

### 当前的变通做法：带 yield effect 的函数式插件

使用函数式的提供方插件，用一个 `ctx.effect(function* () { ... })` 组合服务发布和资源 effect。yield 各个注册返回的那个销毁函数本身，让组合后的 effect 获得它们的所有权：

1. 获取资源和必需的完成监听器，然后 `yield` 每个注册返回的销毁函数。资源清理用 `ctx.effect()` 注册，同样 yield 它返回的那个销毁函数。
2. 最后用 `yield ctx.provide(name, service)` 发布服务。反向销毁时会先撤回服务，等待仍在 Cordis 中注册的依赖方消费者，然后才销毁前面的资源 effect。
3. 如果提供方需要单独的准入闸门，最后 yield 它的清理，这样销毁时会先停止新的准入，再撤回服务。在消费方结束期间，让已接受的清理操作保持可用。

这样能在消费方仍然注册时，安排好提供方撤回的顺序；但它不是完整的外层所有者关闭方案。消费方销毁时，会在清理完成之前就把 fiber 从注册表中移除，所以服务撤回可能漏掉一个正在销毁中的消费方。对于根或外层所有者的销毁，以及独立启动的消费方清理，要通过一个显式的所有者保留并等待实际的消费方销毁任务，然后再释放它们的资源。

即使插件本身就是 generator，也要把这些 yield 放在组合的 `ctx.effect()` generator 里面。在当前实现中，只在插件顶层 yield，销毁函数仍然是并发的同级。不要 yield 包在已注册销毁函数外面的替代包装器：原来的 effect 仍然各自独立拥有，依然可能提前关闭。这个变通做法只为捕获到的 effect 排序；它不能修复没被捕获的、由消费方拥有的监听器，也不能免去处理清理失败的需要。

不要只因为缺少注入、只是"可能"有一个延迟调用却没有可达的消费方，或者有意压制了可选通知，就报告问题。必需的持久化和完成观察者不能当作可选通知。

回归测试的做法：在消费方最后一次使用依赖之前暂停它，开始提供方或外层所有者的销毁，确认资源和必需的监听器仍然可用，然后放行消费方。断言它实际的最终结果和持久化输出，并断言销毁一直挂起，直到消费方完成。既要覆盖提供方卸载或替换，也要覆盖只有消费方清理的情况；只统计调用次数、只测空闲时的正常销毁，都不够。

## 报告

只报告上面三条规则中有充分证据的 P0 违规。给出精确的源码位置、插件根、消费方和资源所有者、会失败的交错顺序、可观察的影响、修正方法，以及确定性的验收测试。多个位置实现的是同一个失败时，合并成一条。说明检查过的范围、被排除的候选和复现的局限；不要因为做过模式搜索就声称已经完全安全。

如果被要求记录尚未解决的问题，用 `proposed/` 下的 Agent Note 记录，写明理由、备选方案、验收标准和风险，并对现有 Note 做取代检查。否则直接返回问题。如果没有确认任何违规，就说明在检查范围内没有发现 P0 违规，并指出任何重要的证据缺口。当调用方提供了结构化的输出 schema 时，按该 schema 使用这里的规则名称和严重级别；执行自动审计之前，先报告相互冲突的规则说明。
