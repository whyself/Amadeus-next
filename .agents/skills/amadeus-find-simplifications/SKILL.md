# 寻找 Amadeus-next 中的简化

寻找能删除维护义务的改动：API、数据表示、生命周期状态、配置路径、依赖、测试或文档。宁可要少数几个证据充分的候选，也不要追求删除数量。这是指导，不是清单；保持在用户给定的范围内，并区分"做一次调查"和"获准实施调查得出的提案"。

## 确定范围和约束

判断之前先读 [根 AGENTS.md](../../../AGENTS.md)、[文档规范](../../../docs/AGENTS.md) 和相关的有效 Agent Note，了解哪些是有意为之的决策；新记录按 [Agent Note 规则](../../notes/README.md) 编写。

范围较大时，按独立的领域分开调查（例如各个插件包、文档门禁脚本、构建与发布流程），每个领域都要给出消费方证据和被排除的备选方案。既要检查明显没用到的符号，也要检查规模较大的生产机制；不要找到第一个看起来可删的东西就停下。

## 寻找可删除的义务

用下面的问题引导发现。候选需要校准时，读 [历史模式](references/historical-patterns.md) 中的相关一节；那些例子说明的是决策方式，不是当前的删除清单。

- **声明的功能有完整的生效路径吗？** 追踪生产者、转换、提供方或端点的支持，以及可观察的结果。一个到处被拷贝的字段，可能根本没有设置它的地方、没有读取它的地方，或者只有拒绝它的实现。除了调用方，还要搜索构造函数和判别字段的产生方。
- **哪些区分会改变消费方的行动？** 多个内部状态可能只需要一个面向模型的状态，或一个可用的标识。控制授权、驻留、持久性或所有权的内部区分要保留；只会诱导出无用选择的公开区分可以删掉。
- **更小的显式行为能否替代整个子系统？** 固定间隔、由调用方提供时区、直接报告激活失败，可以分别去掉通用日历、持久化的默认值或自动回滚。写出放弃的能力和删掉的机制。有生产调用方时，这是一个行为决策，不是自动否决；实施必须在用户授权的范围内。
- **消费方能否在需要时直接读取权威值？** 寻找被拷贝的历史、提升记录、"先发失效事件再读取"的模式，以及与共享投影流并存的功能缓存。改为按需推导或复用，可能同时删掉订阅、保留的数据、过期响应的处理和恢复路径。先确定需要在什么时候观察这个值。
- **是否把组合误当成了策略？** 可选服务是否存在、提供方的某个方法、一个同级工具，都可以表达可用性，而不必决定部署行为。显式配置或表达调用方意图的操作，可能可以去掉注册表和依赖检查。所有权或完成时机不同的操作要保持区分。
- **完整的维护成本归谁？** 追踪透传的配置、重复的应用树、被产品使用的演示启动器、只为解析而存在的 workspace，以及有自己升级周期的安装辅助工具。把整个被删除的系统和替代方案（包括剩余的胶水代码）一起比较；把复杂度挪到别处，或者加一道门禁来保证重复的定义保持一致，都不算删除。

## 证明可达性和取舍

先用 `rg` 搜索，再阅读匹配结果。搜索精确的符号、属性的读和写、判别字段、事件和传输字符串、配置键、包名，以及 `.method(` 和 `method(` 两种形式。测试和类型声明可以说明一个契约，但不能证明存在已发布的生产者或消费者。

搜索范围包括 `packages/*/src`、脚本、`cordis.patch.yml`、包清单和导出、Loader 的解析，以及安装后的包的消费方。按实际入口而不是目录名来判断示例和 fixture 的性质。公开的第三方扩展路径，即使仓库内没有调用点，也可能是有意保留的。

对每个候选，记录当前的所有者、实际生效的生产者到消费者路径、会消失什么、保留什么，以及保留它的最有力理由。区分：

- 删除不可达或没人读取的行为；
- 收窄公开或产品行为，并明确写出损失；
- 受保护的义务，或证据不足。

如果候选破坏了一项需要保留的义务、只是把同样的复杂度挪了个地方，或者没有实质性的减少，就否决它。按提议的改动本身来理解否决理由：过时的清单，或者一个混合提案中被否决的那部分行为，并不能决定每一个独立的条目。重新提出之前要刷新证据。小的局部改进写成可执行的 `TODO`/`FIXME`/`XXX` 注释，不单独写设计记录。

## 保留所有权和失败语义

对于拷贝、冻结、校验器和回调捕获，写出值的来源、下一个所有者和信任边界。同进程、有类型的调用通常只是借用只读值；解析器、配置加载器、队列、模型或工具的 JSON、持久化文件、worker、进程和传输解码器则拥有或校验它们的输入。仅有"恶意 getter"或"回调被替换"之类的测试，并不能单独构成一项需求。冻结了根对象不能证明它的后代不可变，id 相同也不能证明是同一个对象。

对于异步机制，把每个 promise、标志、取消路径、销毁函数和预留，对应到它的所有者和状态转换。只有表达的是同一个事实时，才合并这些机制。在需要的地方，保留同步的发布与回滚、回调异常的隔离、以第一个终态结果为准的裁决、worker 或进程的所有权，以及"销毁要等到静止"。持久化的开始和结束标记可以记录真实发生的事实，即使对话渲染器忽略它们；丢掉被中断的工作是能力损失，不是清理冗余日志。

## 只为净减少而替换基础设施

添加依赖之前，先搜索已有的依赖和引擎下限版本中 Node 内置的能力。写出替代方案会删掉的确切实现和专门的测试、它的维护成本和传递依赖成本，以及胶水代码必须保留的每一个剩余行为。

重点检验最可能让替代方案失效的不一致之处：协议截断、取消和拆除、配置的上限、确定性的测试时钟、平台打包，以及源码入口与构建产物入口的差异。一个库能处理分帧，却需要重新实现同样的分帧来强制大小上限，就不算简化。被接受的边界行为变化，要写进提案和相关测试。不要重新证明依赖的通用规范，却漏掉针对本仓库适配层的测试。

## 记录、合并和验证

涉及文字时使用 [amadeus-prose-standard](../amadeus-prose-standard/SKILL.md)。删掉复述代码或在别处已有归属的解释，同时保留局部的行为、时机、所有权和失败义务。在同一次改动中更新受影响的 README、JSDoc、模型可见内容和配置。

较大的提案使用 `proposed/` Note 的必需骨架：`## 问题`、`## 提案`、`## 考虑过的替代方案`、`## 验收标准` 和 `## 风险`。写入具体的消费方证据、被删除的维护成本、放弃的能力，以及可观察的验收条件。已经做出的决定改用 [implemented 格式](../../notes/README.md#正文骨架)。决定相同时更新已有的归属 Note；不要为了凑候选数量而创建重复的 Note。

每个新 Note 都要按 [Agent Notes 的 AGENTS.md](../../notes/AGENTS.md) 做有范围的取代检查。一次代码调查不等于对整个仓库的 Note 做审计。保留部分取代关系，以及当前仍然有效的持久化、传输、兼容或已否决备选方案方面的义务。

合并另一个分支的成果时，对照目标基线比较它独立的 diff，只移植有证据支持、互不重叠的提案，并合并重叠的理由。关闭别人的 PR 需要授权，或者明确负责这类整理工作。

只改 Agent Note 等文档时，运行 `pnpm run doc-sync`、`pnpm run lint` 和 `git diff --check`；其他检查按 [amadeus-commit-push](../amadeus-commit-push/SKILL.md) 选择。报告调查过的范围、有证据支持的候选、有意义的否决或推迟、新增、合并、保留或删除的 Note，以及实际运行过的命令。不要把未经验证的搜索描述为穷尽的。
